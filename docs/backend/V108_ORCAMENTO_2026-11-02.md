## Escopo

Backend necessário para o Prompt 29 / V1-08 — `/contratos/:id/orcamento`, conforme PRD 4.1, V1-CON-001..005 e transversais de concorrência, paginação, segurança, rastreabilidade e Zero-Drift.

## Lacuna confirmada antes do BUILD

O HML já possuía `propostas_orcamentarias`, `versoes_proposta` e `linhas_orcamentarias`, porém:

- `versoes_proposta` não tinha operação de escrita autorizada ao frontend;
- `linhas_orcamentarias.id_versao_proposta` é obrigatório;
- inexistiam RPCs oficiais de criação/versionamento/publicação do orçamento;
- faltavam os atributos literais `valor_mensal_previsto`, `valor_anual_previsto`, `permite_remanejamento`, `observacoes` e a referência ao documento-base;
- proposta e linhas ainda tinham DML direto concedido a `authenticated`;
- o snapshot de competência não excluía de forma suficiente versões orçamentárias em rascunho.

O frontend não poderia contornar essa lacuna. O backend foi corrigido antes do Lovable.

## Implementação aditiva

### Schema

- `versoes_proposta.id_arquivo_origem` com FK e índice.
- `linhas_orcamentarias` recebeu:
  - `valor_mensal_previsto`;
  - `valor_anual_previsto`;
  - `permite_remanejamento`;
  - `observacoes`;
  - `versao_registro` para concorrência otimista.
- O modelo legado `quantidade`, `valor_unitario`, `valor_total`, `codigo`, `descricao` foi preservado para compatibilidade com o financeiro preventivo/V3.
- Código de rubrica continua opcional na UX; quando ausente, o backend gera identificador estável `RUB-*`.

### RPCs públicas V108

Wrappers públicos `SECURITY INVOKER`, restritos a `authenticated`, com lógica privada `SECURITY DEFINER` e `search_path=''`:

1. `salvar_proposta_orcamentaria_v108`
2. `registrar_versao_proposta_v108`
3. `salvar_linha_orcamentaria_v108`
4. `remover_linha_orcamentaria_v108`
5. `publicar_versao_proposta_v108`

A escrita direta em proposta, versão e linhas foi retirada de `authenticated`; SELECT/RLS foi preservado.

### Segurança e governança

- sessão ativa obrigatória;
- perfil permitido: `administrador`, `gestor_contrato`, `financeiro`, `contabilidade`;
- Administrador Master permanece global via helper central, sem criação de perfil paralelo;
- isolamento por organização/contrato revalidado em toda operação;
- idempotência com hash de payload e replay seguro;
- concorrência otimista em proposta e linha;
- locks server-side em operações materialmente concorrentes;
- hash SHA-256 canônico da versão + documento-base + rubricas;
- publicação exige fundamento humano;
- documento-base pode permanecer `pendente` durante o rascunho, mas precisa estar `aprovado` para publicação;
- versão publicada e suas rubricas tornam-se imutáveis;
- versões anteriores passam a `substituida` sem perda histórica;
- auditoria V108 com `correlation_id`;
- anon não recebe EXECUTE;
- helpers internos não são expostos ao cliente;
- nenhum SQL dinâmico, segredo, Edge Function ou tabela paralela.

### Snapshot temporal

`privado.snapshot_contexto_competencia` passou a:

- ignorar rascunhos orçamentários;
- considerar apenas versões `publicada`/`substituida` aprovadas;
- reconstruir a vigência efetiva usando a próxima versão da mesma proposta sem reescrever o histórico da anterior;
- impedir que o campo auxiliar `proxima_inicio` escape para o JSON oficial.

Edições de rascunho não invalidam portões. A publicação material continua invalidando somente competências temporalmente afetadas.
